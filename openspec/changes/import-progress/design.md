## Context

See proposal.md for motivation. This is the app's first real-time feature — no channel, no
Action Cable route mount, and no frontend Action Cable client exist yet. `ApplicationCable::
Connection` already identifies `current_user` from the signed session cookie (generated by the
Rails 8 auth scaffold in `feature/authentication`, never exercised since).

This branch also reverses an earlier decision: development previously used lightweight
in-process adapters for all three of Solid Queue/Cache/Cable (`async` job adapter, `:memory_
store` cache, `async` cable) specifically to avoid needing extra local databases. Testing this
feature locally against the same `solid_cable` adapter production actually uses is worth that
cost now — see "Development uses the Solid trifecta too" below.

`SpreadsheetImport` and `SpreadsheetImportJob` (from `feature/spreadsheet-import`) are otherwise
unchanged by this branch — the job already updates the record at every meaningful point (each
batch, completion, failure, the `discard_on` path); this branch only adds a way for those
updates to reach the browser.

## Goals / Non-Goals

**Goals:**
- Live-update exactly one page: an import's `show` status page, while that import is
  processing.
- Reuse the exact same "import summary" shape the page already renders from Inertia props, so
  a live update and a page load never disagree about what the data looks like.
- Lay a small, generic foundation (`useChannel`) that `feature/dashboard-realtime` can reuse,
  without building more than this branch actually needs.
- Development runs the same Solid Queue/Cache/Cable adapters as production, so this feature (and
  `feature/dashboard-realtime` after it) is tested against real delivery, not just the
  in-process `async` adapter standing in for it.

**Non-Goals:**
- A list/index of in-progress imports — the app has no such page today (routes are `new`/
  `create`/`show` only), and nothing in the proposal asks for one.
- Editing or retrying an import from the live page — unchanged from `feature/spreadsheet-
  import`.
- Any change to `SpreadsheetImportJob`'s processing logic, batch size, or checkpointing.

## Decisions

### Broadcast explicitly from the job, via a dedicated service — not a model callback

An `after_update_commit :broadcast_progress` callback on `SpreadsheetImport` was the first
draft of this design: one line on the model, and every `update!` the job already performs (four
sites: each batch, completion, failure, the `discard_on` path) would broadcast automatically,
nothing to remember at any call site. Reconsidered and dropped, on reflection that a callback is
the wrong trade here even though it's the less-typing option: it makes broadcasting an invisible
side effect of persistence — nothing at `import.update!(...)`'s call site hints that saving the
record also pushes a WebSocket message, so understanding what a given `update!` actually does
means going and reading the model's callback list, and every other future caller of
`SpreadsheetImport#update`/`#save` (a console session, a future admin action, a test) broadcasts
too, whether that's wanted or not. This is exactly the category of side effect this project's
own conventions already keep out of models — the same reasoning that makes `Users::Inviter` a
service instead of a `User.invite` class method (mailer side effects don't belong in persistence
code paths; a socket broadcast doesn't either).

Instead, `SpreadsheetImport` stays a plain persistence model plus a serializer, nothing more:

```ruby
class SpreadsheetImport < ApplicationRecord
  # ...
  def summary_json
    as_json(only: %i[id status total_rows processed_rows success_count error_count])
  end
end
```

Broadcasting is `app/services/imports/progress_broadcaster.rb`, following this project's usual
service shape:

```ruby
module Imports
  class ProgressBroadcaster
    def initialize(import)
      @import = import
    end

    def call
      SpreadsheetImportChannel.broadcast_to(import, import.summary_json)
    end

    private
      attr_reader :import
  end
end
```

`SpreadsheetImportJob` calls it explicitly, right after each `update!` — kept DRY (not four
copy-pasted two-line blocks) via one small private job method rather than a model callback:

```ruby
def update_and_broadcast!(import, attributes)
  import.update!(attributes)
  Imports::ProgressBroadcaster.new(import).call
end
```

used at all four sites (`update_and_broadcast!(import, status: :processing, ...)`, `...
status: :completed, ...`, `... status: :failed, ...` in the rescue block, and in `discard_on`'s
block). This keeps the "one place to remember" benefit the callback had, but as an explicit,
readable call sitting right next to the `update!` it pairs with, in the class actually doing the
work — not a fact you have to already know to find by opening an unrelated file. The known cost,
accepted deliberately: broadcasting now depends on every update site actually calling
`update_and_broadcast!` instead of `update!` directly — a plain `import.update!(...)` added later
without going through the helper silently skips the broadcast. Worth guarding with a test
(assert every code path in the job broadcasts) rather than solved by making the model do it
automatically. `summary_json` is extracted from `Admin::SpreadsheetImportsController#import_json`
(currently a private controller method with an identical field list) so the controller's props
and the service's broadcasts are provably the same shape — the controller is updated to call
`@import.summary_json` instead of duplicating the field list.

### One channel, one stream per import

```ruby
class SpreadsheetImportChannel < ApplicationCable::Channel
  def subscribed
    import = SpreadsheetImport.find_by(id: params[:id])
    reject and return unless import && current_user&.admin?
    stream_for import
  end
end
```

`stream_for import` (not a hand-built stream name) is the standard Rails idiom — it derives the
broadcast name from the record's GlobalID, matching what `SpreadsheetImportChannel.broadcast_to`
sends to. Authorization mirrors the `show` action exactly: any admin, not only the import's
owner (consistent with admin-user-management's "any admin manages any User" precedent already
used for `show`) — `current_user` comes from `ApplicationCable::Connection`, which already
rejects unauthenticated sockets before a channel is even reached.

### Frontend: a small reusable `useChannel` hook; the socket payload drives state directly

```ts
// app/javascript/hooks/useChannel.ts
//
// A hook (not a plain function/class) because subscribing is tied to a component's lifecycle:
// it has to (re)subscribe when the component mounts or `channel`/`params` change, and always
// unsubscribe on unmount — exactly what useEffect's setup/cleanup pair models. A plain function
// would leave every caller re-implementing that same effect + cleanup by hand.
import { useEffect } from 'react'
import { createConsumer } from '@rails/actioncable'

let consumer: ReturnType<typeof createConsumer> | null = null
function getConsumer() {
  return (consumer ??= createConsumer())
}

export function useChannel<T>(channel: string, params: Record<string, unknown>, onReceived: (data: T) => void) {
  useEffect(() => {
    const subscription = getConsumer().subscriptions.create(
      { channel, ...params },
      { received: onReceived }
    )
    return () => subscription.unsubscribe()
  }, [channel, JSON.stringify(params)])
}
```

Used in `show.tsx` as:

```tsx
export default function AdminSpreadsheetImportsShow({ import: initialImport }: { import: SpreadsheetImportSummary }) {
  const [spreadsheetImport, setSpreadsheetImport] = useState(initialImport)

  // Keeps the manual "Refresh" fallback working: a full Inertia reload lands a fresh `import`
  // prop, which this re-syncs into state. Live updates below never go through this path.
  useEffect(() => setSpreadsheetImport(initialImport), [initialImport])

  useChannel<SpreadsheetImportSummary>('SpreadsheetImportChannel', { id: initialImport.id }, setSpreadsheetImport)

  // ...render from `spreadsheetImport`, not `initialImport`
}
```

Earlier draft of this design used the broadcast only as a signal to trigger `router.reload({
only: ['import'] })`, re-fetching the summary from the server instead of reading it out of the
socket message. Reconsidered: `summary_json` is the one and only serialization of "an import's
summary" — the controller's initial prop and every channel broadcast both come from calling it
on the same record, so there's no drift risk in trusting the socket payload directly; the
reload-based approach was solving a problem (two representations disagreeing) that doesn't
actually exist here, at the cost of a round-trip per update it didn't need to pay. Applying the
payload straight to local state is both simpler and more "live" — no network request between a
broadcast landing and the page reflecting it.

`useChannel` is intentionally generic (channel name + params + callback) rather than a
`useSpreadsheetImportChannel`-specific hook, since `feature/dashboard-realtime` (independent,
parallel branch per the roadmap) will need the same subscribe/unsubscribe lifecycle for a
different channel and payload shape (the `<T>` type parameter is what lets each caller keep its
own payload type without `useChannel` itself knowing about `SpreadsheetImportSummary`). Only
what's needed now is built; no channel registry or reconnect/backoff logic is added
speculatively — `@rails/actioncable`'s consumer already retries the underlying WebSocket
connection on its own.

### Progress bar

The status page gains a visible bar (`processed_rows / total_rows`, clamped to 0–100%, showing
0% while `total_rows` is still `null` before the job has parsed the file) alongside the existing
text counts — the roadmap names this feature "progress bar via Solid Cable" specifically, not
just live-updating text.

### Development uses the Solid trifecta too

Reversing the earlier "development stays lightweight" choice: `development` now uses
`solid_cache`, `solid_queue`, and `solid_cable` — the same adapters as production — instead of
`:memory_store`/`async`/`async`. Reason: this branch's whole point is testing real Action Cable
delivery, and `async` cable already works fine in-process for that, but it doesn't exercise the
actual adapter production uses (message persistence/polling via `solid_cable_messages`); running
the same adapter locally is worth the setup cost now that we're building on it directly.

**Four Postgres databases, same as production — the conventional, recommended shape**, not a
shared-database shortcut. `config/database.yml`'s `development:` block becomes a multi-database
config mirroring `production:` exactly, just with local database names:

```yaml
development:
  primary:
    <<: *default
    database: umanni_development
  cache:
    <<: *default
    database: umanni_development_cache
    migrations_paths: db/cache_migrate
  queue:
    <<: *default
    database: umanni_development_queue
    migrations_paths: db/queue_migrate
  cable:
    <<: *default
    database: umanni_development_cable
    migrations_paths: db/cable_migrate
```

`bin/rails db:create` provisions the three new databases against the same Postgres instance the
Docker Compose setup already runs — no compose/service changes needed, `CREATE DATABASE` is
just SQL against a connection that already exists. `bin/rails db:schema:load:cache`/`:queue`/
`:cable` then load the existing, unmodified `db/{cache,queue,cable}_schema.rb` files into their
respective databases — verified directly (created the three databases, loaded each schema,
confirmed via a raw `pg` connection to each database that its tables landed correctly with no
diff on any `db/*_schema.rb` file).

Two single-database shortcuts were tried first and rejected — kept here briefly since they were
real, evidence-based dead ends, not just untried ideas:
- **All four roles pointing at one shared database** (same database, no Postgres-schema
  namespacing) — broke Rails' own bookkeeping: `schema_migrations`/`ar_internal_metadata` are
  physical tables shared across every role pointing at the same database, so `db:migrate:queue`
  found the primary app's migration versions already present, concluded queue's own migrations
  were already applied, and never created a single `solid_queue_*` table. Worse,
  `db:schema:load:queue` (run while diagnosing this) **dumped the primary app's own schema over
  `db/queue_schema.rb`** — caught and reverted before anything was committed, but a clear sign
  this path is actively unsafe.
- **One shared database, isolated by Postgres schema (namespace) per role** — this one actually
  worked when verified directly (tables landed correctly, isolated, no corruption). Dropped
  anyway after further research: it's not how Rails' multi-database support is meant to be used
  and isn't the documented/recommended pattern, so it was traded for the conventional four-
  database shape instead, matching production exactly rather than being a clever one-off.

The rest follows the same shape as before: `config.cache_store`/`config.active_job.
queue_adapter`/`config.solid_queue.connects_to` in `config/environments/development.rb` to
match `production.rb`, `cable.yml`'s `development:` block switches to `solid_cable`, and
`jobs: bin/jobs` returns to `Procfile.dev` (removed in `feature/users-admin-crud` specifically
because the queue database didn't exist yet — it will now). `test` is intentionally untouched:
`ActiveJob::TestAdapter` and cable.yml's `test: adapter: test` are testing tools, not related to
which store backs them in a running process, so switching them to Solid would only make tests
slower for no benefit.

## Risks / Trade-offs

- **[Local multi-database setup is more moving parts than before]** → `bin/rails db:prepare`
  now provisions four Postgres databases instead of one; a missing/out-of-date `cache`/`queue`/
  `cable` database now surfaces as a real boot error in dev rather than silently not existing.
  Accepted as the cost of dev matching production exactly; `db:prepare` handles all of them from
  a clean checkout in one command, same as it already does for `test`.
- **[A dropped WebSocket connection silently stops live updates]** → acceptable: the page still
  shows correct data on any reload (see the "live updates require no reload, but a reload always
  shows the truth" scenario) — this is a UX degradation (back to manual refresh), never a
  correctness issue, and `@rails/actioncable` already reconnects on its own without app code.
- **[Explicit `update_and_broadcast!` calls can be skipped by a future `update!` that bypasses
  it]** → the trade-off taken on deliberately by rejecting the callback approach (see the
  Decisions section above): nothing structurally forces every future write to broadcast. Task
  3.4 covers this with a test asserting each of the job's four update paths actually broadcasts,
  so a regression here fails a test rather than surfacing as a silently-stale status page.

## Migration Plan

Purely additive: no schema change, no data migration. Deploys like any other code change;
rollback is reverting the commits (no backward-incompatible state was introduced).
